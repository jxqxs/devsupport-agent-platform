# Week 2 场景题

题目来自 `word/03_DevSupport_knowledge_and_interview_tutorial.md`。下面按面试时口头讲的方式写，术语保留。

## 1. Day 1｜volatile 为什么不能代替 AtomicInteger？

我会先把两件事分开。`volatile` 解决的是看见看不见，`AtomicInteger` 解决的是这一次加减会不会被别人插一脚。

`volatile` 的意思是：一个线程把变量写完，别的线程马上能读到新值，编译器和 CPU 也不能随便把这次读写挪到别的地方。它管的是可见性和一部分顺序。它不管「读出来、在自己脑子里加 1、再写回去」这三步是不是一次做完。

`count++` 看起来是一行，实际是读、加、写。两条线程可以同时读到 100，都算出 101，都写回去。最后还是 101，有一次加丢了。加 `volatile` 只是让它们都看见最新的 100，读和写之间那段空档还在，所以顶不上 `AtomicInteger`。

`AtomicInteger.incrementAndGet()` 走的是 CAS。线程先记住自己读到的数，准备写的时候再看一眼内存里是不是还是这个数。是，才把新值写进去。不是，说明别人已经改过了，这次作废，拿新值再试。它比一把锁轻，但这一次更新不会丢。

本周我拿两条线程各加 10 万次试过。普通 `int` 的 `count++` 跑出来是 `129104`，离 `200000` 差一截，而且每次数字都不一样。换成 `AtomicInteger` 就是 `200000`。所以共享计数这种读改写，我用原子类。`volatile` 我留给状态标记，比如「停不停」，那种只写一个新值、不依赖旧值的场景。

## 2. Day 2｜线程池 Queue 持续增长怎么办？

队列一直变长，说明任务进得比出得快。我不会先把最大线程数调大，先把原因顺着这条线看完：

任务是不是提交得太猛，平均一条要跑多久，现在有多少线程真的在干活，队列已经堆了多少，下游的数据库或者 HTTP 是不是变慢了，连接池是不是拿不到，超时设得合不合理，有没有几条特别慢的任务把工人拖住。

这里要分两种队列。`newFixedThreadPool` 用的是不封顶的队列。核心线程占满以后，新任务全进队列，最大线程数根本排不上，队列就可以一直涨，最后把内存吃掉。有界队列不一样：核心满了先进队列，队列满了才把线程加到最大数，还满才拒绝。本周用 `ArrayBlockingQueue`，容量 100 的时候 100 个工单都接住了，`callerRuns` 是 0。容量只有 2、核心 2、最大 4 的时候，池子同时大约只能咬住 6 个任务，多出来的才走到拒绝。

拒绝也要看这个任务能不能扔。能扔，用 `DiscardPolicy` 直接丢掉，或者用 `AbortPolicy` 抛 `RejectedExecutionException`，让调用方自己决定重试。不能扔，又希望提交慢下来，用 `CallerRunsPolicy`。池子满的时候，`submit` 不返回，提交这次任务的线程自己把活干完。它被按在任务上，后面的提交暂时进不去，工人就有时间把队列清一清。本周那组小池子，100 个任务里有 30 个是 `main` 自己跑的，日志里是 `main id6` 这种。`main` 一睡，队列空出位置，后面的任务又能进池子，所以不是 100 个全堆在主线程上。

线程数不是越大越快。线程一多，切换变多，每条线程还有自己的栈。数据库连接、HTTP 连接、下游的承受能力都是有上限的。上游把池子开得很大，下游先被打满，队列照样涨。所以我先找慢任务和下游，确认是消费跟不上，再决定池子大小和拒绝策略。

## 3. Day 4｜Java CPU 100% 怎么查？

CPU 打满时，我要的是「哪个线程、哪段代码在转」，所以按这个顺序收：

先用 `top` 找到那个 Java 进程的 PID。再用 `top -Hp PID` 看这个进程里面哪条线程最吃 CPU。线程号是十进制的，`jstack` 和 Arthas 里的 nid 是十六进制，要转一下才能对上。然后 `jstack`，或者进 Arthas 打 `thread`，最好是 `thread -n 3` 看最忙的几条栈。

栈对上以后再判断它在干什么。常见的是死循环、一直在做 GC、空转、正则回溯，或者 JSON 序列化特别重。锁如果竞争得很厉害，线程会在自旋里空转，CPU 也会高。GC 的话，Arthas 的 `dashboard` 上能看到年轻代、老年代回收了几次、停了多久。线上不能只看平均响应时间，暂停会体现在 P95、P99 上。

死锁我单独看。死锁的线程多半堵在等锁上，状态是 `BLOCKED` 或者 `WAITING`，CPU 往往不高。本周那个一直跑的 `ArthasDemo`，`main` 大部分时间在 `Thread.sleep(1000)`，`thread` 里它是 `TIMED_WAITING`，CPU 接近 0，堆只用了大约 19MB。那是正常在等，不是热点。

线程池的配比也会把 CPU 打满，但那是看完栈之后的判断。纯计算的活，线程数比 CPU 核数大很多，时间就耗在切换上。等数据库、等 HTTP 的活，线程可以多一些，因为大部分时间在等。多也有限度，连接池和下游容量到了，再加线程只是更多人在排队。

## 4. Day 5～6｜这条查询很慢怎么办？

```sql
SELECT *
FROM support_tickets
WHERE status='OPEN'
ORDER BY created_at DESC
LIMIT 20;
```

我会先 `EXPLAIN`，把执行计划摊开，再决定加什么索引。一条线上的慢查询，我按这个顺序讲：数据有多少，`status` 的值分得匀不匀，现在有哪些索引，要不要联合索引，`ORDER BY` 能不能借到索引的顺序，`SELECT *` 会不会回表回得很狠，最后拿真实数据压一次。

本周这张表是 10 万行虚拟工单，三次 `EXPLAIN` 是这样的。

只有主键的时候，`type` 是 `ALL`，`key` 是空的，估计要看 `99775` 行，`Extra` 是 `Using where; Using filesort`。翻译过来就是：二级索引用不上，把表扫一遍，再用 `where` 留下 `OPEN`，最后为了 `created_at DESC` 单独排一次序，再取 20 条。

加上 `INDEX(status)` 之后，`type` 变成 `ref`，`key` 是 `idx_status`，估计行数掉到 `49887`。`OPEN` 大概一半，所以还是要看很多行。更关键的是 `Extra` 里还有 `Using filesort`。这个索引只按状态分好堆，同一个状态里面的创建时间是散的，排序省不掉。所以「慢就给 `status` 加个索引」这句答不全。

再加 `INDEX(status, created_at)`，优化器在两个索引里选了 `idx_status_createAt`。`type` 还是 `ref`，估计行数还是 `49887`，但 `Extra` 变成 `Backward index scan`，`filesort` 没了。联合索引不是两个独立索引，它是先按 `status` 排，状态相同再按 `created_at` 排。`OPEN` 这一段里面时间已经有序，`DESC` 就倒着读这段索引。`LIMIT 20` 不会把 `rows` 改成 20，`rows` 是优化器觉得 `OPEN` 有多少行。真正执行时，倒着读、凑满 20 行就可以停。

还有两件事要说清楚。第一，`SELECT *` 要整行，二级索引叶子上一般只有索引列和主键，找到之后还得拿主键回表。如果列表页只展示状态、时间和标题，可以把这些列放进联合索引，做成覆盖索引，少回表。第二，联合索引的顺序跟查询走。前面的列如果是范围条件，后面的列就不再有序。这条 SQL 是 `status` 等值，再按 `created_at` 排序，所以写成 `(status, created_at)`。写成 `(created_at, status)`，就用不顺这次的 `WHERE`。
